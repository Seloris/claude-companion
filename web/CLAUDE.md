# web — the dashboard: every Claude Code workspace, its sessions and their recap

```component
kind: front
stack: react-express
skin: aurora
layers: [data, pages, ui]
commands:
  build: npm run build
  lint: npx eslint {files}
  prepare: npx openapi-typescript ../api/openapi.json --output src/api/schema.d.ts
  serve: npm run dev
```

All commands run from this component's path. The front has no unit tests: never create a `*.test.tsx`. Lint only the files a stage changed, never the whole app.

## Structure

```
src/
  main.tsx                  the theme imports first, then the React root, QueryClientProvider, RouterProvider
  AppLayout.tsx             the root layout route: the shared navigation (NavBar, with the live counts) around every page
  router.tsx                the route tree under AppLayout, one lazy route per feature page
  api/
    schema.d.ts             generated by `prepare` from the API's OpenAPI document: never edited by hand
    client.ts               the openapi-fetch client (`createClient<paths>`), base URL, auth header, problem-details handling
  features/{feature}/
    data/                   query and mutation hooks over the client (`use{Entity}Query`, `use{Action}Mutation`), query keys
    pages/                  routed pages (`{Name}Page.tsx`)
    ui/                     presentational components (props in, callbacks out), forms (`{Name}Form.tsx`)
  shared/
    ui/                     shared components, one {Name}.tsx and its {Name}.module.css per element of the skin's recipes; labels are props, no className prop, no feature word
                            Panel, PageTitle, Field (label, error, the control as a render prop), TextInput, SearchInput, Select,
                            Button (variant: primary, danger, quiet, ghost), Switch, Checkbox, List (List, ListItem with isDone, ListItemText),
                            Badge (tone: default, attention, muted), Banner (a warning strip, role="status"), EmptyState, LoadingState, ErrorMessage (role="alert"), ConfirmDialog (a native <dialog>),
                            NavBar (the navigation: links as props, counts as `badges`), ButtonLink (an <a> with the button's look, variant: quiet, ghost), Disclosure (a native <details>, folded until opened),
                            Tabs (a tab list with counts), ChipGroup (toggle chips that pick one item), icons.tsx (SearchIcon, TrashIcon, ChevronIcon, QuestionIcon, CheckIcon, EyeIcon, BranchIcon, DesktopIcon, CopyIcon)
      theme/                fonts.ts (the skin's font imports) and skin.css (its tokens), both written by factory-init: never edited; base.css (the page), overrides.css (this application's values)
    lib/                    utils, i18n; useNow.ts (the current time, re-read every interval), useClipboard.ts (copy text, with its copied/failed state), desktopLink.ts (isDesktopLink: the only desktop-app href the pages render)
```

## Conventions

- **TypeScript strict**, function components, hooks; no default exports except where React Router's lazy routes need them; no `any`.
- **Data:** a page uses its feature's `data/` hooks; the hooks are the only place that calls the API client; the client is the only place that calls `fetch`. Server state lives in TanStack Query (one query-key factory per feature, every mutation invalidates or updates the queries it changes); local UI state in `useState`/`useReducer`; no global store unless several features share client state.
- **Types** of requests and responses come from `src/api/schema.d.ts` (`paths`, `components["schemas"][...]`), never redeclared by hand.
- **Pages** are routed, thin, and compose UI components; **UI** components receive props and emit callbacks: no data hook, no client call inside them.
- **Forms:** one `{Name}Form.tsx` per form, holding its fields, validation and the mapping of the API's problem details (`400` field errors) to field messages.
- **i18n:** every user-facing string goes through the translation layer; keys live in `src/shared/lib/i18n/{lang}.json`, named `{feature}.{element}.{text}`; a missing key is a review finding.
- **Styling:** CSS Modules (styles scoped to their component; no global style outside `src/shared/ui/theme/`). Styles read the skin's variables only: no literal color, radius, shadow, font family or control height (see Design).
- **Loading and errors:** every page that reads data shows a loading state and an error state; a failed mutation shows the problem details' message.
- File naming: `PascalCase.tsx` for components and pages, `camelCase.ts` for hooks and utils (`useOrdersQuery.ts`).

## Design

The skin named in the `component` block above: its fonts in `src/shared/ui/theme/fonts.ts` and its tokens in `skin.css` beside it (both written by factory-init, rewritten by `/factory:factory-init skin`), imported first by `main.tsx`, then `base.css` and `overrides.css`. The UI follows the factory plugin's design rules (`reference/ui-design.md`), its element recipes (`skins/recipes.css`) and the skin's `SKIN.md`, read in place; this section wins over them. Features compose the `shared/ui` components and style only their own layout; a recipe or a component two features need that `shared/ui` lacks is added there, in the same way.

- Variables this application changes: in `src/shared/ui/theme/overrides.css`, never in `skin.css`.
- Rules this application adds or replaces: here, one line each.
- A `ButtonLink` ghost hovers toward the text color (`--text`, `--surface-2`), not the ghost button's `--danger`: an open action is not destructive. `ButtonLink` combines `Button.module.css`'s classes in code, never `composes … from` (it makes the build warn).
- A command to copy by hand uses `--font-mono` (`overrides.css`; the skin has no monospace token).
- Warnings use `--warning` and `--warning-soft` (`overrides.css`, aliased to the live page's amber), never `--danger`.
- The live page and its navigation use `--live-width` (1360 px): its board needs three columns; every other page keeps `--content-width`.

## Testing

- No unit tests on the front: the `test-in-browser` skill checks a change in the real app on http://localhost:5180; there are no test accounts, nothing to sign in with.

## Local run

- Prerequisites: Node 22, `npm ci`.
- Run: `npm run dev` → http://localhost:5180; the API must be running on http://localhost:3100 (`test-in-browser` starts both when they do not answer).
- The root's `npm run build` builds the front into `dist/` (after `prepare`), and `npm start` there has the API serve it on http://localhost:3100; the dev server stays the way to work on the front.
- `prepare` regenerates `src/api/schema.d.ts` from the API's committed handoff file; run it at the start of every front stage.
